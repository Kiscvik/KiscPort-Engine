# KiscPort Probe 1.4.0

KISC-LABS, 14 November 2026. A small public MIDlet that tells what a Java ME phone can do for a KiscPort port:
platform, APIs, audio, M3G performance (and Mascot Capsule v3 if the phone has it) and memory. It saves a report and
PNG screenshots on the phone itself. It contains nothing from any game: the sounds are synthetic
(`scripts/make_probe_sounds.py`) and the meshes and textures are generated by code on the phone. It includes the
old MMAPI diagnostic 1.0.0 as its sound part.

Probe's on-screen text is in Spanish; this document quotes it as shown, with a translation where useful.

## Building

```sh
python3 scripts/make_probe_sounds.py   # only if the test sounds change (deterministic output)
python3 scripts/build_probe.py         # dist/probe/KiscPortProbe.jar / .jad (~84 KB)
python3 scripts/smoke_probe.py         # FreeJ2ME-Plus: tests the logic, not the phone
```

It installs next to any game (different `MIDlet-Name`, it replaces nothing). Same rules as the engine: CLDC 1.1,
MIDP 2.0, Java 1.3, bytecode 45.3 and StackMap preverification. M3G, Mascot Capsule v3, MIDIControl, OpenGL ES and
FileConnection are loaded by name: if the phone lacks one, only that part fails, and Probe says why.

## Using it

| Key | Action |
|---|---|
| Joystick up/down | Move the selection or scroll the text |
| OK (joystick centre) | Choose |
| Left or «Atrás» (Back) | Back to the menu |
| Numbers | Shortcut: each entry's number |
| `#` (or «Captura») | PNG screenshot of the current screen |
| `*` (or «Parar sonido») | Stop all sound |

Each screen's footer lists its keys and shows notices (screenshot saved, report saved…).

| Menu | What it does |
|---|---|
| 1 Prueba rápida (quick test, recommended) | Information + graphics tests 1–5 + saved report, hands-off, about 2 minutes. Ends on the report |
| 2 Información del teléfono (phone information) | Properties, APIs present, M3G, OpenGL ES, audio controls and formats, in one list |
| 3 Gráficos 3D (M3G, Mascot) | The performance tests, one at a time or all; under each one, its result. Test 8 compares M3G with Mascot and gives a verdict; test 7 is the full Mascot Capsule v3 run |
| 4 Sonido (sound) | WAV formats (entry 0) and the 9 MMAPI tests. After each one, the question «¿Qué oyó?» (what did you hear?) appears with its answers |
| 5 Memoria (memory) | Explains the risk and starts with OK |
| 6 Informe y capturas (report and screenshots) | The full report; OK saves it as `kiscport-probe.txt` |
| 7 Registro (log) | Everything that happened, with times |
| 8 Ayuda (help) | Keys and how to send the results |

Recommended order for a new phone: **1** → **4** (answer what you hear) → **5** if you accept it may close the
app → **6** to save the final report.

## Screenshots

`#` saves the current screen as `kiscport-001.png`, `kiscport-002.png`… On the benchmark's 3D screen, `0` saves the
next frame as `kiscport-3d-001.png`… (`kiscport-mc3-001.png`… in the Mascot test) and `*` (asterisk) stops the
test. **Other keys do nothing:** they keep the screen from turning off during a long test without ending it. (Up
to 1.3.0 any key stopped it, including the answer to the permission question when saving a screenshot on the
W900i.) Files go to the first file root that accepts them (memory card or phone memory); the phone may ask for
permission, because the MIDlet is not signed.

- **Probe only.** MIDP 2.0 cannot read other apps' screens. To capture a game, add the same code to the game
  (`PngWriter` + drawing the frame into an `Image`).
- **How it works.** The screen is redrawn into a mutable `Image` of the same size; `PngWriter` reads it row by
  row with `getRGB` and writes an uncompressed RGB PNG (~230 KB for 240×320). Besides the image, it holds only one
  row in memory.
- **The captured 3D frame is not timed.** Drawing into an `Image` may take a different path in the driver than
  drawing to the screen, so it is done separately and the measuring window moves forward by the time it took.
- The mutable image costs about 150–300 KB while the capture lasts; on a phone with little memory the capture
  may fail, and the footer and the Log say so.

## Performance tests

Each step draws for 2 s after 0.5 s of warm-up. A frame is `bindTarget` + clear + draw + `releaseTarget` +
`flushGraphics`, timed with the millisecond clock. Probe reports FPS, average ms per frame, the render part
(without the screen flush) and the slowest frame. A series stops if a step goes over 500 ms per frame, and no step
lasts more than 20 s. The 3D screen shows the test and «Paso N de M» (step N of M).

| No. | Test | What it answers |
|---|---|---|
| 1 | Meshes of 12, 96, 192, 384, 768, 1,536 and 3,072 triangles, same screen area, QUAD submission | How many triangles per frame the phone can take |
| 2 | The same 768 triangles sent three ways: one strip per triangle, per quad (QUAD, the engine's) and per row | What each strip costs the driver |
| 3 | Checker textures from 16 to 512 px (up to `maxTextureDimension`) on 384 triangles | Creation time, memory used and drawing cost; where it fails |
| 4 | A still square, larger than the screen, drawn 1, 2, 4 and 8 times without depth test | The cost of pixels alone (overdraw) |
| 5 | 425 and 1,617 vertices rewritten every frame against the same still mesh | The cost of CPU skinning for an animated character |
| 7 | Mascot Capsule v3: the meshes of test 1 as QUADS, the 768 triangles as TRIANGLES and as QUADS, textures from 16 to 256 px on 384 triangles and the fill of test 4. Only if the phone has `com.mascotcapsule.micro3d.v3`; otherwise it says so | Whether HI Corporation's proprietary API is faster than M3G on that phone |
| 8 | The same four loads with M3G and with Mascot: 768 and 3,072 triangles, a 128 px texture on 384 triangles and the screen filled 4 times | **Which API suits this phone**: ends with a verdict |
| 9 | 1 to 5 in a row | Full pass (the one in the quick test) |
| Memory | 64 KB blocks reserved up to 8 MB or until `OutOfMemoryError` | How much Java memory a port can really use |

### Mascot Capsule v3 against M3G

Test 7 repeats the M3G tests with the same mesh, the same screen area, the same turn and the same measurement, so
both can be read side by side (its lines start with `MC3`). A frame is a `fillRect` clear + `bind` +
`renderPrimitives` + `flush` + `release` + `flushGraphics`. Differences carried inside the numbers:

- `renderPrimitives` takes unshared vertices and at most 255 primitives per call (the mesh is split into batches,
  prepared before timing);
- one colour per face (in M3G, per vertex and smoothed), no lighting;
- 8-bit paletted BMP textures, generated on the phone (M3G: RGB), up to 256 px;
- no depth buffer: the API sorts the polygons;
- no vertex upload test: in Mascot vertices travel with every call, so their cost is already in the other tests.

The view angle is computed so the mesh covers the same pixels as in M3G (60° vertical), and the first line reports
it. If an implementation applies the angle differently, the mesh will come out at another size: the `0`
screenshot shows it. Only the API's basic calls are used, so a name missing on some phone does not break the whole
test; if a step fails it says `NO` and why, and the series continues or stops. It is not part of the quick test.

Results measured on the W995 and W900i, and why the engine keeps M3G for production while studying Mascot, are
in [ENGINE.md](ENGINE.md#why-m3g-and-why-mascot-is-being-studied).

### Verdict: M3G or Mascot (test 8)

Each load is measured with both APIs, by **whole frame time** (not just "render": on the W995, M3G leaves part of
its work for `flushGraphics`). An API wins a load if it is at least 15 % faster. The verdict adds up the times of
the four loads, as if each were done once:

```
CMP mallas 768 tri: M3G 36.2 ms, Mascot 20.4 ms -> Mascot 1.7x mas rapido
VEREDICTO para este telefono: Mascot Capsule v3, 1.9x mas rapido en total (gana 4 de 4)
```

(«mas rapido» = faster; «VEREDICTO para este telefono» = verdict for this phone; «gana 4 de 4» = wins 4 of 4.)
With less than 15 % difference the verdict is «empate: M3G, el estándar» (tie: M3G, the standard). If the phone
lacks one of the two APIs, the other wins and Probe says why. The verdict appears at the top of the Graphics list,
in the footer notice and as `VEREDICTO 3D` at the start of the report. These are synthetic meshes: they say which
API draws faster on that phone, not how a particular game will run.

The memory test can close the app on some phones; that is why it has its own screen with a warning and is not part
of the quick test. If the app closes, the last value in the Log is the approximate limit. On these phones the Java
heap grows on demand: `freeMemory` at start does not tell how much fits, the total reserved does.

## Report

One line per item: Probe's identity, platform and known properties, memory at that moment, M3G properties, APIs
present, sound results (API and what was heard, separately), performance results and saved screenshots. If fast
phases were used (emulator only), it says so.

To send results: `kiscport-probe.txt` and the screenshots, in a GitHub issue with the model and firmware. The data
feeds the device profile ([ENGINE](ENGINE.md)): usable memory, triangles per frame, safe texture size, cost of
strips, fill and skinning, audio formats and mixing. Each item is a **measurement on that phone**; Probe measures
the driver in isolation, not a game's section loading, animation or HUD.

## Validation 1.4.0

PC and FreeJ2ME-Plus, 14 November 2026: `build_probe.py` passes the audit and `smoke_probe.py` passes 104 checks:
those of 1.3.0, test 8 through to its verdict (which also appears in the report), and that on the 3D screen `*`
stops the test and other keys do not. In the emulator the times are the PC's and the verdict is marked as not
valid. **Not yet tested on a phone.**

## Validation 1.3.0

PC and FreeJ2ME-Plus, 14 November 2026: the package passes the audit (also, only `MascotBench` refers to
`com/mascotcapsule`) and `smoke_probe.py` passes 98 checks: those of 1.2.0 and test 7 in fast mode, with its four
series and a requested screenshot. In the emulator's screenshots the Mascot mesh covers the same area as the M3G
one, and the texture and fill are drawn. Without the API, the test says so before taking the screen. FreeJ2ME
brings its own Java reimplementation of Mascot and cannot start without it, so the "no Mascot" case is checked by
construction (loaded by name, only one class uses it), not by running it. Afterwards, test 7 was run on the W995
and the W900i (both have Mascot); those results are in [ENGINE.md](ENGINE.md#why-m3g-and-why-mascot-is-being-studied).
The emulator's times say nothing about a phone.

## Validation 1.2.0

PC and FreeJ2ME-Plus, 13 November 2026: the package passes the audit (bytecode 45.3, StackMap, only
`kiscport/probe/` and `snd/`) and `smoke_probe.py` passes 94 checks:
- navigation with joystick, OK, shortcuts and back to the menu;
- the 9 sound tests with their question screen;
- the 5 performance tests in fast mode, with a requested 3D screenshot;
- memory;
- the quick test, which ends on the report;
- the PNG of two real screens, read back (240×320 and with content).

FreeJ2ME turns the file root into a path from the disk's `/`, so nothing can be saved there: the test checks that
Probe says so, and validates the PNG encoder separately. **Not yet tested on the W995 or the W900i**, where real
saving will be checked (permission, memory card or phone memory).
